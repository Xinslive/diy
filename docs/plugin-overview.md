# 插件开发总览

插件是运行在财务记账系统里的受信任扩展。一个插件可以同时提供后端接口、自己的前端页面、独立的数据表和账套级配置；宿主负责用户授权、账套权限、会计校验、文件留存和最终提交。

当前公开契约为 **SDK 1.2.0 / CWP 1**。如果你第一次开发插件，建议先阅读“快速开始”，完成一个最小插件，再回到本页和 API 参考查具体能力。

## 适合构建什么

插件适合把一项相对独立的业务流程接入系统，例如：

- 读取当前用户有权访问的账套，并提供自定义查询或业务页面；
- 在插件自己的表中保存账套配置、业务记录和处理结果；
- 接收文件，解析为凭证草稿，让用户检查、调整、确认后整批提交；
- 在期末结账等宿主事件发生后记录插件自己的审计事件。
- 注册由外部每分钟 tick 驱动的周期任务；宿主会按当前有效插件授权逐用户执行。

插件负责业务规则和交互，宿主负责最终的权限判断、账务校验和事务边界。插件不需要复制宿主的登录逻辑，也不应该直接操作宿主数据库。

## 一个插件包含什么

| 部件 | 是否必需 | 用途 |
|---|---:|---|
| `plugin.json` | 是 | 声明插件身份、兼容的 SDK、权限、入口、菜单和数据表 |
| `backend/main.py` | 是 | 导出 `register(registrar, ctx)`，注册插件自己的 HTTP 接口和 hook |
| `frontend/index.js` | 否 | 导出接收 `host` 的组件工厂，提供插件页面 |
| `migrations/versions/*.py` | 按需 | 创建或升级插件自己的数据表 |
| `frontend/style.css`、图片等 | 按需 | 前端静态资源；必须随包签名 |

插件源目录用于开发，`.cwp` 是上传格式。签名工具会根据源目录生成文件清单和签名字段，源目录里的 `plugin.json` 不要手工填写 `files` 和 `signature`。

## 一次请求会经过哪些检查

1. 用户必须已登录，并且被管理员授予该插件的使用权。
2. 插件只能访问 manifest 中声明的 capability；未声明的 `ctx` 属性不会提供。
3. 读取或写入账套时，宿主再次检查用户对目标账套的角色和状态。
4. 凭证写入会复用宿主的科目、期间、金额精度和借贷平衡校验。
5. 文件导入的确认、提交和来源追溯由宿主保存，插件只负责解析规则和页面交互。

授权和账套权限是两层独立判断。页面上的 `canWrite` 只能用于调整按钮状态，不能代替后端校验。

## 开发前需要知道的边界

插件代码属于受信任代码：Python、迁移和同源前端 JavaScript 在宿主的运行环境中执行。签名、扫描和窄 SDK 用于控制发布来源与误装风险，不能把插件变成安全沙箱。只安装经过组织内部审阅的包，并把私钥放在受控的打包环境中。

前端使用预编译、自包含的 ESM。插件不能在运行时加载 CDN、远程模块或 SFC 编译器，也不能依赖未随包提供的 npm 包。

### 后端代码到底能拿到什么

安装时的静态扫描按**白名单**收敛插件的 import：只有规范里列出的模块可以 import，其余一律拒绝；同时禁止 `eval`、`exec`、`compile`、`__import__`、`getattr`、`open` 这类「先取名再调用」的写法，禁止下标取函数（`func["eval"](...)`），也禁止 `posix.execv` 这类危险属性访问。

因此**插件后端代码不能** import `sqlalchemy`、`psycopg2`、`app.*` 或任何宿主模块，也拿不到宿主的 SQLAlchemy session、数据库连接或任意 SQL 接口。宿主也不把 session 交给插件：插件只能用 `ctx` 上按 manifest 权限开放的能力。

但这是**静态扫描的第一道防线，不是沙箱**：

- 它拦的是**明显的等价入口**。经过编码混淆的等价写法、宿主自身依赖里的漏洞，仍可能绕过；扫描不构成对恶意代码的隔离。
- **运行期还有第二层**（2026-10-25 补）：插件代码在**裁剪过的环境**里执行。拿到的模块是**代理**（按能力清单裁过属性），`__import__` 是**受控版本**（只放行清单里的模块）；白名单模块上挂着的**别的模块**（`dataclasses.sys` / `uuid.os` / `json.codecs` 这类）一律拿不到；含双下划线的**反射形态**（`__globals__` / `__builtins__`）在**装载期**就拒装。这一层把「绕过扫描的几条常见等价写法」也堵住了，但**它同样不是隔离边界** —— 它只覆盖已知的那些形态，同进程同权限这件事没有变。
- 插件与宿主**默认同进程、同操作系统权限**（`PLUGIN_ISOLATION=off`）：插件仍然可以耗尽 CPU/内存/线程，影响核心服务。
- **插件迁移是唯一的例外**：迁移由宿主 alembic 以宿主连接执行，因此只开放 `op` 的 DDL 能力；`op.execute`、`op.get_bind` 和自行开数据库连接（`sa.create_engine`）都被扫描拒绝。插件迁移只能改自己声明的表。
- 要真正抵抗恶意第三方插件，必须改为独立服务/容器、独立数据库身份与进程间 API。当前方案不满足这个目标。

### 隔离模式（2026-10-25 补）

宿主用 `PLUGIN_ISOLATION` 决定插件后端代码的**执行位置**，三种取值：

| 取值 | 插件后端代码在哪 | 说明 |
|---|---|---|
| `off`（默认） | 宿主进程内 | 与历史一致 |
| `shadow` | 宿主进程内 + 另起一个 worker 进程跑同一份代码 | 只比对两边声明的差异，不改对外行为 |
| `on` | **只在 worker 进程里** | 宿主按 worker 报上来的声明重建路由，请求经 Unix socket 派活 |

`on` 模式把「插件 RCE 打穿宿主」的爆炸半径从整个宿主进程缩到一个 worker 进程 —— 但**它不是安全边界**：worker 与宿主是同一个操作系统用户、同一套文件权限，能碰的东西与进程内模式几乎一样。真正的边界（容器 / seccomp / landlock / 独立数据库身份）**尚未实现**。切换 `PLUGIN_ISOLATION` 不需要重新打包插件，插件源码零改动。

worker 自己会带上三条限制（并把**实际生效**的结果报回宿主，便于核对）：不产生 core dump（core dump 里可能有账套数据与令牌）、文件描述符有上限、Linux 上禁止通过 setuid 提权。systemd 层的隔离（只读文件系统、私有 tmp、只允许 AF_UNIX、按 unit 限进程数）**尚未实施**。

## 安全边界速查

下表是仓库内插件风险登记册的摘要。完整登记册与逐条验收证据保存在仓库的插件文档里，不随公开页发布；本页只保留读者判断「敢不敢装这个包」所需的那部分。

| 风险 | 已交付的控制 | 仍然存在的边界 |
|---|---|---|
| 插件读取秘密、破坏数据、提权 | 签名 + 人工审阅、import 白名单、危险调用与属性形态拦截、运行期模块代理裁剪 + 受控导入器 + 装载期反射复核、窄 SDK、按 manifest 授权 | 静态扫描不是沙箱；运行期裁剪也只覆盖已知形态；同进程代码可绕过扫描之外的等价写法，资源耗尽会影响核心 |
| 插件迁移伤及宿主 | 只允许 `op` 的 DDL；`op.execute`/`op.get_bind`/自行开连接被拒；迁移范围反射与真实 FK 校验 | 迁移在宿主连接上执行；宿主自身的 DDL 校验不是数据库权限隔离 |
| 签名密钥泄露 | 撤销名单在安装期**和加载期**都判定；管理动作可一键封禁并停用 | 已运行代码不会自动停止；停用需要重启全部 worker |
| 插件表结构漂移拖垮备份 | 备份目录按域降级：漂移插件被跳过并在归档头留痕 | 含漂移插件的归档不能恢复，必须先修复漂移再重新备份 |
| 备份与隔离区撑满 | 备份/隔离区不占插件代码配额，有独立额度与清理入口 | 清理只删不再被引用的备份；仍被引用的备份一律保留 |
| 管理员能管理但不该自动使用插件 | 独立授权名单，安装后零授权，管理员不豁免 | 管理员可以显式给自己授权，审计记录该操作 |
| 同源 JS 读取登录态 | 自包含 ESM、固定资产 URL、现有 CSP | 同源代码具有 origin 权限，public asset 不是隔离边界 |

## 验收登记册（摘要）

| 门禁 | 验收证据 |
|---|---|
| 整包签名 | 改 Python/JS/迁移/资源、未知/撤销密钥、路径与容量攻击均被拒绝 |
| import 白名单 | 非白名单模块、`eval`/`exec`/`__import__`/`open`、下标取函数、危险属性访问全部被拒；两个真实插件源码通过 |
| 撤销生效 | 撤销 key_id 后新包装不上，已安装插件在重启后拒绝加载（`KEY_REVOKED`） |
| 备份分域隔离 | 一个插件的表漂移不再让全部账套与系统备份失败；含漂移的归档在恢复前被拒绝 |
| 存储配额 | 备份与隔离区不计入代码配额，清理入口只删除无引用的备份 |
| 资产访问 | 插件前端资产凭短期票据访问，匿名请求 401，资产按 digest 缓存核验 |

逐条重跑命令与结果记在仓库的插件验证文档里。

## 从第一个插件到可发布包

1. 创建源目录和 `plugin.json`。
2. 写后端入口；需要页面时再加入前端入口。
3. 为插件表写线性迁移，并在 manifest 中声明表的 scope。
4. 用开发环境跑通接口、权限和错误处理。
5. 用 Ed25519 私钥构建并验证 `.cwp`。
6. 由管理员安装、授权用户并重启服务。
7. 检查插件状态、菜单、账套权限和失败路径。

页面目录按这条路径组织。先看“快速开始”，需要精确字段时看“Manifest、权限与运行时参考”，处理文件转凭证时看“数据导入 API”。

## 版本与兼容

`version` 使用 SemVer；`api_version` 声明插件接受的 SDK 范围，例如 `>=1.2.0 <2.0.0`。升级插件时，宿主会重新验证包、迁移和数据表结构；插件应把配置格式和数据变更写进迁移，避免在启动时偷偷改表。定时任务的详细契约见 [插件规范](plugin-spec.md)。
